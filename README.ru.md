# Personal Tideway

[English version](README.md)

Personal Tideway — локальный слой непрерывности для пользователей, которые
переключаются между Codex и Antigravity (`agy`). Его цель — дать обоим агентам
одинаковый отобранный контекст проектов, общие skills, rules и MCP без
копирования целых диалогов и без служебных данных внутри репозиториев с кодом.

> **Статус разработки:** pre-alpha. В репозитории уже есть протестированный
> фундамент конфигурации и синхронизации, а явная живая передача checkpoint
> между Codex и agy подтверждена. Долговечный автоматический assurance, фоновая
> синхронизация и упаковка публичного релиза ещё не готовы. Перед изменением
> живых конфигов проверяйте dry-run и план резервного копирования.

## Как это должно работать

1. Вы открываете Git-репозиторий, обычную папку или инфраструктурную задачу.
2. Personal Tideway определяет проект и выдаёт небольшой релевантный контекст.
3. Вы работаете в Codex или agy.
4. Важные решения, состояние и следующие шаги сохраняются локальным checkpoint.
5. Позже работу можно продолжить с любым из двух агентов без повторного
   исследования проекта.

Инструмент хранит отобранные факты и checkpoints, а не журналы чатов.

## Что уже есть

Реализовано и покрыто автоматическими тестами:

- версионированная центральная конфигурация с определённым приоритетом;
- единое рабочее пространство вне исходных проектов со строгой защитой границ
  путей и выхода через symlink;
- обнаружение актуальных установок Codex и agy без изменения клиентских файлов;
- детерминированный реестр и идентификация проектов для Git-репозиториев,
  обычных каталогов и явных внешних проектов;
- изолированная установка фиксированной версии Basic Memory 0.23.2, проверка
  работоспособности и синхронизация реестра с конфигурацией без неявного main или
  default;
- явный процесс переиндексации (reindex) и JSON-отчёт о статусе каждого проекта;
- доступное только для чтения получение ограниченного контекста и компактная
  идемпотентная запись состояния проекта через Basic Memory;
- безопасный CLI-мост для получения ограниченного контекста проекта (`ptw context show`,
  `ptw context search`) и идемпотентного сохранения checkpoint (`ptw checkpoint`);
- практический проверенный workflow передачи состояния (checkpoint handoff) между Codex и agy через CLI-мост и обработчики начального контекста (см. [CHECKPOINT_HANDOFF.md](docs/CHECKPOINT_HANDOFF.md));
- каноническая общая политика непрерывности и минимальный навык непрерывности,
  создаваемые при init и проецируемые через sync на Codex и agy;
- типизированная оценка assurance с подтверждением свидетельствами и отображением
  статусов instructed, manual или unavailable в status и doctor без ложных заявлений о хуках;
- безопасная инициализация нативного хука жизненного цикла Antigravity CLI (`ptw hook install`,
  `ptw hook remove`, `ptw hook status`, `ptw hook plan`) и ограниченный обработчик PreInvocation;
- безопасная инициализация нативного хука жизненного цикла Codex (`ptw hook install --client codex`,
  `ptw hook remove --client codex`, `ptw hook status --client codex`, `ptw hook plan --client codex`) и ограниченный обработчик SessionStart (`ptw hook codex-session-start`);
- детерминированная, доступная только для чтения оценка Projection Parity в `ptw status` с раздельными результатами для MCP, правил и навыков для Codex и agy, безопасной ремедиацией и сохранением portable MCP parity;
- явное планирование миграции v1→v2, транзакционный apply, сохраняемые backup-manifest
  и публичный rollback с dry-run, проверенные на обезличенных временных home-каталогах;
- безопасные режимы dry-run и fail-closed границы во всех операциях;
- ранний движок MCP, rules, skills, конфликтов, backup и dry-run;
- полный набор успешно проходящих автоматических тестов и реальное одноразовое
  smoke-тестирование.

Ещё предстоит реализовать:

- долговечная верификация assurance хуков для живых клиентов (evaluator возвращает `instructed`, `manual` или `unavailable`; одноразовый зонд функциональности не повышает автоматически статус живой установки без подтверждённых свидетельств наличия, активации, доверия и актуального дайджеста);
- автоматический перехват при завершении сессии (stop/exit) на уровне нативных хуков (клиенты в настоящее время не предоставляют нативного события Stop; сохранение чекпоинтов остаётся явным/instructed через CLI);
- непрерывная фоновая синхронизация rules, skills и MCP;
- установщик, онбординг, CI и публикацию релизных артефактов для публичной
  alpha.

Порядок работ находится в [ROADMAP.md](ROADMAP.md).

## Интеграция жизненного цикла Codex

Personal Tideway интегрируется с Codex CLI (живая проверка выполнена на 0.155.1) через его нативный контракт хуков ([документация по хукам Codex](https://learn.chatgpt.com/docs/hooks)):

- **Команды жизненного цикла:** `ptw hook plan --client codex`, `ptw hook install --client codex`, `ptw hook status --client codex` и `ptw hook remove --client codex` (флаг `--dry-run` поддерживается для `install` и `remove`; клиентом по умолчанию остаётся `agy`).
- **Целевой файл хуков:** Управляемые хуки размещаются в `$CODEX_HOME/hooks.json`, а установка включает обязательную настройку `features.hooks = true` в `$CODEX_HOME/config.toml`, сохраняя посторонний TOML. Опциональный флаг `--codex-hooks` принимает пути строго внутри `$CODEX_HOME` с лексической валидацией отсутствия выхода за пределы через symlink.
- **Контракт событий:** Обрабатывается исключительно одно событие `SessionStart` с регулярным выражением матчера `^(startup|resume|clear|compact)$`, запускающее обработчик `ptw hook codex-session-start`.
- **Безопасность парсинга и сериализации:** Строгий лимит 256 КиБ на файлы конфигурации хуков JSON и TOML, а входной payload из stdin ограничен 64 КиБ; для обоих форматов JSON действует ограничение максимальной глубины вложенности 64 (формат TOML ограничен парсером со стандартными исключениями без явного лимита глубины). Сторонний JSON-контент семантически сохраняется. Запись файлов хуков атомарна, а резервные копии создаются перед внесением изменений. Установщик выполняет только добавление и удаление своей строго идентифицированной управляемой группы. Дубликаты, модифицированные записи и коллизии инлайн-команд Tideway приводят к остановке с ошибкой (fail-closed).
- **Слои конфигурации и модель доверия:** Слои хуков Codex аддитивны (не переопределяют друг друга); команды с совпадающими условиями могут выполняться параллельно. Проектные хуки выполняются только в доверенных проектах (trusted projects). Пользовательские хуки требуют ручного подтверждения через `/hooks` или первичного окна проверки доверия в TUI Codex. Установщик никогда не генерирует хеши доверия и не обходит проверки клиента. Отключение хуков или политика managed-only могут предотвратить их запуск.
- **Границы обработчика:** Обработчик `codex-session-start` обслуживает строго зарегистрированные проекты (без автоматической регистрации), игнорирует дампы диалогов и выполняет ровно один ограниченный запрос контекста (не более 5 элементов, до 8000 символов), возвращая payload события `hookSpecificOutput` с полем `additionalContext`.
- **Статус assurance и поведенческого зонда:** Наличие установленных хуков в `ptw status` или `ptw doctor` сообщает статус строго среди `instructed`, `manual` или `unavailable` (`hook_verified` остаётся `False`; уровня `incapable` в evaluator не существует). Изолированный одноразовый зонд функциональности успешно пройден 15.09.2026 без обхода защит (см. [CODEX_HOOK_PROBE.md](docs/CODEX_HOOK_PROBE.md)). 24.09.2026 backed-up живая приёмка подтвердила точную передачу скрытого маркера из Codex в agy и обратно через нативные хуки начального контекста, включая нативное review доверия Codex и финальный обычный запуск Codex без флагов обхода feature или trust (см. [MIGRATION_5E_LIVE_ACCEPTANCE.md](docs/MIGRATION_5E_LIVE_ACCEPTANCE.md)). Этот поведенческий успех всё ещё не повышает assurance автоматически до `hooked`, потому что evaluator пока не сохраняет и не проверяет долговечные свидетельства зонда.
- **Следующие шаги:** Долговечные поведенческие свидетельства и интеграция жизненного цикла stop/checkpoint остаются отдельными этапами, после них — упаковка публичной alpha.

## Восстановление после миграции

Миграция выполняется только явной командой оператора. Перед применением нужно
изучить план и dry-run. Успешный apply выводит bundle ID и путь к manifest;
rollback принимает любое из этих значений.

```bash
ptw migrate plan
ptw migrate apply --dry-run
ptw migrate apply
ptw migrate rollback <bundle-id-или-путь-к-manifest> --dry-run
ptw migrate rollback <bundle-id-или-путь-к-manifest>
```

До любых изменений rollback проверяет manifest и хеши backup, восстанавливает
исходные bytes и права, удаляет созданные транзакцией пути и сохраняет новые
файлы центральной памяти. Для машиночитаемого отчёта к любой команде можно
добавить `--json`. Транзакционные apply и rollback проверены на сгенерированных
fixtures. Живая приёмка 24.09.2026 использовала backed-up fresh-install путь,
поскольку текущий workspace уже имел schema v2, а `ptw migrate plan` вернул
`not_required`; живой rollback не потребовался и не выполнялся. Для миграции
живых клиентских home-каталогов по-прежнему нужны отдельно согласованные backup
и план приёмки.

## Хранение данных

Все данные Personal Tideway находятся внутри `PERSONAL_TIDEWAY_HOME`
(по умолчанию `~/.personal-tideway`):

```text
~/.personal-tideway/
  config.yaml
  secrets.env
  registry/projects.yaml
  projects/
  knowledge/personal/
  mcp/
  rules/{shared,codex,agy}/
  skills/{shared,codex,agy}/
  services/basic-memory/
  state/
  conflicts/
  backups/
  locks/
```

При обычной работе Personal Tideway не должен создавать своё состояние или
данные Basic Memory внутри зарегистрированных исходных проектов.

## Среда разработки

Нужны Linux, Python 3.11 или новее и `uv`.

```bash
git clone https://github.com/Jykez/personal-tideway.git
cd personal-tideway
uv sync --extra test
uv run ptw --version
uv run pytest -q
```

Для экспериментов используйте временные каталоги:

```bash
export PERSONAL_TIDEWAY_HOME=/tmp/ptw-home
export CODEX_HOME=/tmp/ptw-codex
export GEMINI_HOME=/tmp/ptw-gemini
uv run ptw init
uv run ptw status
uv run ptw sync --dry-run
```

Не храните ценные данные в этих демонстрационных путях.

## Модель безопасности

- `secrets.env` создаётся с правами `0600` и игнорируется Git;
- OAuth остаётся в собственном хранилище каждого клиента;
- неизвестная новая версия схемы отклоняется без перезаписи;
- до изменений инициализация проверяет весь набор целевых путей;
- конфликтующие объекты изолируются и не блокируют остальные;
- dry-run не должен менять файлы, состояние, backup и timestamps.

Проверки безопасности работают только во временных каталогах:

```bash
uv run --with pytest pytest -q
uv build
```
