# Практический протокол передачи контекста (Checkpoint Handoff)

Этот документ описывает рабочий runnable workflow сохранения состояния проекта одним клиентом
(Codex или Antigravity / `agy`) и восстановления другим клиентом через CLI Personal Tideway.

---

## 1. Общий принцип и архитектура

Personal Tideway хранит **курированные факты и текущее состояние проекта (`Current State`)**,
а не сырые транскрипты бесед или дампы файлов.

Передача контекста строится вокруг канонической заметки `current-state` в Basic Memory:
1. **Клиент А (например, Codex)** завершает задачу или сессию и явно сохраняет компактный чекпоинт
   через `ptw checkpoint --stdin --project <project-id>`.
2. **Personal Tideway** валидирует схему, проверяет отсутствие секретов, рассчитывает семантический
   хэш (fingerprint SHA-256) и атомарно записывает заметку в изолированное хранилище проекта.
   Если чекпоинт идентичен предыдущему, запись пропускается (`unchanged: true`).
3. **Клиент Б (например, agy)** запускается в том же проекте. На этапе инициализации
   (`PreInvocation` у agy или `SessionStart` у Codex) хук начального контекста или явный вызов
   `ptw context show` читает актуальный `Current State` со всеми решениями, блокерами и следующим шагом.
4. **Клиент Б** продолжает работу с единой точки контекста без необходимости заново исследовать проект.

---

## 2. Формат данных CheckpointPayload

Входные данные чекпоинта передаются строго в формате JSON со схемой `CheckpointPayload`:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `condition` | string | Да | Текущее фактическое состояние окружения/проекта (до 4000 символов). |
| `objective` | string | Да | Активная непосредственная цель или этап (до 4000 символов). |
| `completed` | string[] | Нет | Список проверенных выполненных решений и изменений (до 50 пунктов). |
| `blockers` | string[] | Нет | Список активных препятствий и внешних блокировок (до 50 пунктов). |
| `verification_status` | string | Нет | Статус верификации: `"verified"`, `"partial"`, `"planned"`, `"blocked"`. |
| `next_safe_action` | string | Нет | Конкретный безопасный следующий шаг для продолжения (до 4000 символов). |
| `source_client` | string | Нет | Источник чекпоинта: строго `"codex"` или `"agy"`. |
| `evidence` | string[] | Нет | Относительные пути к тестам/логам/файлам (без абсолютных путей и `..`). |

> [!IMPORTANT]
> **Правило статуса верификации:** Непроверенные изменения или результаты с незаконченными проверками
> запрещено сохранять со статусом `"verified"`. Используйте `"partial"` при частичном прогрессе
> или `"blocked"` при наличии препятствий.

## 3. Пошаговые runnable примеры передачи через stdin

Чтобы избежать уязвимостей командной оболочки (shell interpolation, подстановка `$VAR` или обратных кавычек),
рекомендуется использовать передачу JSON через stdin с экранированным heredoc (`cat <<'EOF' | ...`):

### Сценарий А: Codex завершил этап и фиксирует проверенное состояние (`verified`)

```bash
# Предварительная проверка без записи (dry run)
cat <<'EOF' | ptw checkpoint --stdin --project my-project --dry-run --json
{
  "condition": "Модуль авторизации реализован, модульные тесты успешно пройдены",
  "objective": "Реализация сервиса токенов OAuth2",
  "completed": [
    "Настроена генерация асимметричных ключей RSA",
    "Реализован валидатор JWT токенов"
  ],
  "blockers": [],
  "verification_status": "verified",
  "next_safe_action": "Подключить валидатор к HTTP-роутеру",
  "source_client": "codex",
  "evidence": [
    "tests/test_auth.py:42",
    "src/auth/jwt.py"
  ]
}
EOF

# Реальная запись чекпоинта
cat <<'EOF' | ptw checkpoint --stdin --project my-project --json
{
  "condition": "Модуль авторизации реализован, модульные тесты успешно пройдены",
  "objective": "Реализация сервиса токенов OAuth2",
  "completed": [
    "Настроена генерация асимметричных ключей RSA",
    "Реализован валидатор JWT токенов"
  ],
  "blockers": [],
  "verification_status": "verified",
  "next_safe_action": "Подключить валидатор к HTTP-роутеру",
  "source_client": "codex",
  "evidence": [
    "tests/test_auth.py:42",
    "src/auth/jwt.py"
  ]
}
EOF
```

Ответ CLI при успехе:
```json
{
  "project_id": "my-project",
  "project_name": "my-project",
  "fingerprint": "a3f5...",
  "written": true,
  "unchanged": false,
  "dry_run": false,
  "timestamp": "2026-09-16T18:00:00Z",
  "source_client": "codex"
}
```

### Сценарий Б: agy выполняет задачу, сталкивается с блокером и фиксирует состояние (`partial`)

```bash
cat <<'EOF' | ptw checkpoint --stdin --project my-project --json
{
  "condition": "HTTP-роутер подключен, исчерпан пул соединений с тестовой БД",
  "objective": "Подключить валидатор к HTTP-роутеру и связать с БД",
  "completed": [
    "Смонтированы маршруты /api/v1/auth"
  ],
  "blockers": [
    "Таймаут соединения с PostgreSQL на порту 5432 при параллельных запросах"
  ],
  "verification_status": "partial",
  "next_safe_action": "Проверить настройки max_connections в postgresql.conf",
  "source_client": "agy",
  "evidence": [
    "logs/router.log:88",
    "config/database.yaml"
  ]
}
EOF
```

## 4. Восстановление контекста принимающим клиентом

При переходе к следующему клиенту контекст восстанавливается двумя путями:

### 1. Автоматически через начальные хуки жизненного цикла
- **Codex:** При старте сессии хук `SessionStart` (событие `startup`, `resume`, `clear`, `compact`)
  вызывает `ptw hook codex-session-start`, который передает в модель актуальный `Current State`
  через поле `additionalContext`.
- **Antigravity (agy):** При первом вызове модели (`PreInvocation`, `invocationNum == 0`)
  вызывается `ptw hook agy-preinvocation`, который передает `Current State` через `ephemeralMessage`.

### 2. Явно через CLI Personal Tideway
Если хуки отключены или агент работает в среде без поддержки хуков:
```bash
# Получить текущее состояние проекта (по умолчанию до 8000 символов)
ptw context show --project my-project

# Поиск по заметкам и решениям проекта
ptw context search "OAuth2" --project my-project
```

## 5. Честные ограничения и гарантии безопасности

> [!WARNING]
> **Текущие архитектурные ограничения:**
> 1. **Отсутствие native Stop hook auto-capture:** Ни Codex CLI, ни Antigravity CLI в текущих версиях
>    не имеют надежного и подтвержденного события «завершение сессии / остановка агента» с возможностью
>    вызова сторонних бинарников для гарантированного автоматического сброса памяти.
> 2. **Уровень доверия (Assurance Level):** Статус непрерывности (`ptw status` / `ptw doctor`) честно
>    сохраняет уровень `instructed` или `manual`. Успешное выполнение интеграционных тестов или одноразовых
>    зондов **НЕ** повышает статус до `hooked`.
> 3. **Требование явного сохранения:** Агент или пользователь обязан явно вызвать `ptw checkpoint`
>    в конце задачи или при возникновении блокера. Нельзя рассчитывать на неявное фоновое сохранение.
> 4. **Fail-Closed при ошибках:** Если бэкенд недоступен, диск переполнен или раннер завершился с кодом != 0,
>    Personal Tideway возвращает ошибку. Агенту **запрещено** заявлять пользователю об успешном сохранении
>    при возникновении ошибки CLI.
> 5. **Защита от утечек секретов:** Любые попытки поместить токены (GitHub, AWS, Bearer) или приватные ключи
>    в поля чекпоинта блокируются встроенным сканером секретов еще до вызова бэкенда.
> 6. **Сохранение пользовательских правок:** Файлы правил (`continuity.md`) и навыка (`continuity/SKILL.md`)
>    не перезаписываются при повторных вызовах `ptw init` и `ptw sync`, если они уже существуют на диске.
